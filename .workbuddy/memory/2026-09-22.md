## 又发现：/api/acquisition/cached 首次调用 6 秒（既有缺陷）

实测首次 **6209ms**、再查 5ms。隔离定位：
- `DataAcquisition()` 构造 **6027ms**；构造后各 source `is_available()` 仅 0~1ms（构造时已探测缓存）
- 6 秒全在构造阶段：build 数据源时对网络 fetcher 逐个 TCP 探测，
  `freeserv.dukascopy.com` + `api.binance.com` 不可达**各卡满 3s** = 6s

**荒谬点**：`list_cached()`（`acquisition.py:749`）只是扫目录（`iterdir()`+`stat()`），
却因写成 `return _get_acquisition().list_cached()` 而被迫构造会做全网探测的单例。
修法方向：抽出不依赖实例的目录扫描函数，模块级入口自己解析 cache_dirs（走 config accessor）。

### 已修（commit e629c2c）

  与 `_cache_dirs_from_config()`（走 `config.data_acquisition_config().cache_dir`，env 铁律未破）。
- 模块级 `list_cached()` 改为不再碰 `_get_acquisition()`；`DataAcquisition.list_cached()` **保留**并委托同一函数，
  已断言两者结果完全相等（避免两条路径行为分叉）。
- **实测：首次 6209ms → 161ms（我复核）/ 97ms（工程师测），再查 19ms；纯 `list_cached()` 首次仅 1.0ms**；
  `_acquisition` 仍为 None（确实没构造单例）。与 inspect 仍 0 处不一致。
- 测试 948 collected / 945 passed（943 基线 +2）。新增「list_cached() 不得构造单例」守护（改回即变红）。

`/api/acquisition/sources?profile=CRYPTO_BTC` 仍 **6068ms**：构造 `DataAcquisition` 时

### 教训：单例惰性构造的隐性成本
`_get_acquisition()` 这类"模块级快捷入口 → 单例"写法很方便，但**单例构造若含网络探测/重 IO，
会让任何用到它的轻量调用都被拖慢**。凡是"只是读本地信息"的入口（列目录、读配置）都不该走单例。
同理需警惕：`list_sources()` 仍走单例，但它确实需要网络能力，属合理。
### 判断要点（可复用）
- 文件列表接口遍历所有文件，**绝不能用 `load()` 全量加载**，只读需要的那一列。
- 新增"时间范围"类展示时，**必须先确认既有的 UTC 口径并复用同一个格式化函数**，
  否则同一文件两处会差一天，且极难发现。
- 缓存阈值：本次 137ms 未达 300ms 阈值仍加了缓存——因为文件数一多必然超，正确。

### 结论（可直接引用）
- **真断档 0 处**：6 个文件的所有缺口都是周末休市（周六 04:00→周一 06:00 ≈50h）或日休市，无漏数据。
- **H1 / H4 / M15 / M30 / M30_FX_IDC 互相自洽**：M15 vs M30 同刻开盘价 **100% 严格相等**；对 H1 偏移 +0h，
  中位偏差 ~0.20。
- **H1 vs M30/M15/H4 存在 ~0.20 系统性溢价**（83% 为正）：疑似 ask/bid 或不同抓取批次快照差异，幅度小但混用会有系统性偏差。
- **XAUUSD_M5 两个独立缺陷**：
  1. **时间戳偏移 +5h**（2024-01~2026-08 恒定；2026-09 那批为 +0h、偏差 0.000）→ 不同批次抓取拼接，旧批次时区口径错。
  2. **价格数据本身错**：把 5h 偏移修正后与 H1 聚合比对，close 中位偏差 6.24、**90.8% 的小时差 >$1**、最大 250.92；
     内部连贯 |open-前close| 中位 0.0554 但 **5278 处跳变 >$1（2.7%）**、最大 71.12 —— H1 同口径仅 7 处（0.09%）。
     → **不是偏移问题，是插针/坏数据**，做回测会产生大量不存在的止损信号，**不可用**。
- 各文件密度都是理论最大值 ~90%（排除合成数据嫌疑）。

### 关键方法论（这次踩了坑，务必记）
- **别拿"重采样比对"当判据前，先做偏移搜索**。我一开始用固定口径 resample 比对，报出「7567 处不一致、最大偏差 317」，
  吓得我以为数据崩了；实际是口径错。**先搜 ±12h 最优偏移，再看偏差**，否则误报。
- **区分"正常休市"与"真断档"**：外汇周末休市 ~50h，日休市 ~2h。用固定小时上限会满屏误报。
  正确做法：按缺口区间内**是否含周六**分类，再对非周末缺口套上限。
- **判定"哪个文件是错的"要用多数派**：4 个文件互相吻合（含 100% 严格相等），1 个文件孤立，
  那 1 个就是坏的——比跟某个单一基准比更可靠。
- 我自己的脚本连续踩 3 个 bug：numpy 数组用 `and`/`or`、`np.flatnonzero` 索引越界、
  `resample` 需要 DatetimeIndex（整数 index 报 TypeError）。写体检类脚本别用内联 `-c`，直接落文件。

## MT4/MT5 桥接现状（用户问能否从挂着 EA 的 MT 取数）

**答案：可以，且是根治方案；但当前代码库里没有桥接。**
- `data/sources/parquet_mt.py` **只是阅读器**，假设 parquet 已落盘。
  契约：文件名 `{symbol}_{timeframe}.parquet`、列 `time/open/high/low/close/volume/tick_volume`、
  `time<1e7 → ×1000`、`tick_volume` 优先、float32。MT 导出符合契约 → **零新增阅读器代码**。
- 全库无 bridge 实现：`adapters/shenji/contract.py` 里 `core.bridge` 只是**预留占位名清单**
  （故意不 import，因 `MT4BridgeBase` 有 9 个抽象方法，多继承会把导出类带歪）。
  WebUI「MT4 桥接未连接」指妙算侧的桥，不在本库。
- 从自己 MT 取数能根治 M5 那类问题：同一经纪商 feed、同一时基，跨周期天然自洽，不会出现混批次。
- 路径：MT5 有官方 `MetaTrader5` Python 库（无需 EA，`copy_rates_from_pos` 直接读终端）；
  MT4 无 Python 库，需 EA + `WebRequest` POST 到 localhost。

### 协议实证（来自 EA 源码，不是猜的）
- 请求 `F042#-#<sym>#<tf>#<offset>#<count>!`；**tf 传 MT4 整数周期**（H1=60），不是 "H1"。
- 响应 `F042#OK#<t$o$h$l$c$v>#...##`（末尾两个空字段）；`iTime==0` 即历史边界，返回空页**不是异常**。
- `F020` = `F020#OK#<TimeCurrent>#ask#bid#bid#0#` —— **最后那个数值位 EA 填的是 bid 不是点差**（免费 EA 缺陷）。
  实盘验证确认：XAUUSD ask=4330.15 bid=4329.75，spread 位=4329.75。**客户端照实透传**，测试有守护断言。
- 经纪商时区 **GMT+3**（F020 的 TimeCurrent 实测 +3h），与既有 parquet 的 GMT+8 基准一致（8+5-3…即 broker+5=parquet）。
